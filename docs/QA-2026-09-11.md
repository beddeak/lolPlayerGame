이는 현재 데이터 상태에 대한 검사이며 아래 상황이 미래에 발생하지 않는다는 뜻은 아니다.

격리 E2E는 임시 DB 생성 → 23개 migration 적용 → schema 검증 → HTTP 테스트 → 임시 DB 삭제
순서로 실행되었다. 개발 DB에는 SELECT만 실행했다.

실제 브라우저 도구의 앱/브라우저 목록은 비어 있었다. 프론트 검증은 실제 컴포넌트 코드를
변환하여 React SSR, 모의 hooks/API, 실제 handler 실행으로 수행했다. DOM 클릭 검증은 아니다.
추가 백엔드 재현은 실제 서비스/컨트롤러와 메모리 repository/service mock을 사용했으며,
아래 8개 문제 모두를 MySQL E2E로 재현했다는 의미는 아니다.

## 발견 사항

### 1. 시장이 닫힌 시기의 주전 계약 만료로 세이브 진행 중단 — 높음

- 위치: `backend/src/transfers/transfers.service.ts:725`, `backend/src/transfers/transfers.service.ts:465`,
  `backend/src/matches/matches.service.ts:218`, `backend/src/calendars/calendars.service.ts:135`.
- 연중 재계약은 서명일부터 N년 뒤 만료되므로 시즌 중 만료가 가능하다.
- 후보가 없는 주전이 자연 만료되면 FA로 이동한다. 시장이 닫혀 FA 재영입은 거부되고,
  주전 5명이 없어 경기도 거부되며, 미완료 경기 때문에 다음 시장까지 날짜 진행도 거부된다.
- 실제 서비스 재현 결과:
  - 자연 만료: `currentTeamId=null`, 계약 `EXPIRED`, 로스터 없음.
  - 재영입: HTTP 409, 이적시장 기간 제한.
  - 경기: HTTP 409, `does not have a complete starting roster`.
  - 날짜 진행: `2027-02-04`, `advancedDays=0`, `MATCH_DAY`.
- 대응 방향: 부전패 처리 또는 긴급 충원 등 진행 복구 규칙이 필요하다. 어떤 규칙을 적용할지는
  게임 설계 선택이며 이번 검사에서는 임의로 변경하지 않았다.

### 2. 직접 시리즈 API로 리그 경기를 완료하면 다음 단계가 갱신되지 않음 — 높음

- 위치: `backend/src/match-series/match-series.controller.ts:70`,
  `backend/src/match-series/match-series.service.ts:100`,
  `backend/src/leagues/leagues.service.ts:303`.
- `POST /match-series/:id/games/simulate`는 시리즈를 완료시키지만 `progressLeague()`를 호출하지 않는다.
- 해당 라운드 마지막 경기를 이 경로로 끝낸 뒤 정상 리그 경기 API를 호출해도 이미 완료된
  시리즈라는 409가 단계 갱신 전에 발생한다.
- 재현: 시리즈 `COMPLETED`인데 `leagueCurrentRound=1` 유지. 정상 fixture 경로 재호출도
  `MatchSeries 70 is already completed` 409로 종료.
- 현재 화면의 Quick Sim은 정상 리그 경로를 사용한다. 이 오류는 공개된 직접 시리즈 API 사용 시 발생한다.
- 대응 방향: 리그 소속 시리즈의 직접 실행을 제한하거나 모든 완료 경로에서 리그 상태를 동기화한다.

### 3. BO5 2승 시점에 감독 피드백을 잘못 차단 — 중간

- 위치: `backend/src/match-series/match-feedback.service.ts:240`.
- 완료 판정이 `teamAWins >= 2 || teamBWins >= 2`로 고정되어 있다.
- BO5 2:0에서 실제 `MatchFeedbackService.create()` 호출 결과:
  `409 MatchSeries 70 is already completed`.
- 경기는 남아 있지만 다음 세트 전 피드백을 못 한다.
- 대응 방향: 다른 시리즈 처리처럼 `getSeriesWinsRequired(series.bestOf)`를 사용한다.

### 4. 플레이오프 순위가 최종 성적 대신 총승수로 정렬됨 — 중간

- 위치: `backend/src/leagues/leagues.service.ts:1204`, `frontend/src/SeasonHubView.tsx:665`.
- 6시드가 5/4/3/2시드를 차례로 이긴 뒤 결승에서 1시드에 패한 GAUNTLET 결과를 재현했다.
- 실제 결과는 1시드 우승, 6시드 준우승이지만 계산 결과는 6시드 4승으로 1위, 1시드 1승으로 2위다.
- 화면은 이 `rank`를 그대로 표시한다. 국제대회 티켓 자동 배정까지 틀렸다고 검증한 것은 아니다.
- 대응 방향: 정규리그 승수 순위와 토너먼트의 우승/탈락 단계 순위를 분리한다.

### 5. 세이브 전환 후 늦은 응답이 이전 세이브를 다시 띄움 — 중간

- 위치: `frontend/src/App.tsx:215`, 같은 유형 `frontend/src/App.tsx:208`.
- A의 갱신 요청이 대기 중일 때 B를 열고, 뒤늦게 A 응답이 오면 조건 없이 `setActiveCareer(A)`한다.
- 실제 App handler에 응답 순서를 제어하여 `activeCareer.id=2`에서 지연 응답 후 `1`로 돌아가는 것을 확인했다.
- 사용자는 B를 열었다고 생각하지만 후속 행동이 A에 적용될 수 있다.
- 대응 방향: 세션/선택 세이브의 요청 세대를 확인하여 오래된 응답을 폐기한다.

### 6. 커리어 생성 후 목록 조회 실패가 중복 생성으로 이어짐 — 중간

- 위치: `frontend/src/App.tsx:175`.
- POST 생성 성공 뒤 목록 GET만 실패하면 생성 화면에 남는다. 사용자가 다시 제출하면 새 POST를 보낸다.
- 실제 handler 재현: 첫 POST 성공 후에도 `view=create`, `activeCareer=null`; 재제출 후 POST 호출 수 2회.
- 대응 방향: 생성 성공 즉시 반환된 커리어를 열고, 목록 갱신 실패는 별도 오류로 처리한다.

### 7. 만료일 뒤로 미룬 재계약 응답이 무효화되지 않음 — 중간

- 위치: `backend/src/contracts/contracts.service.ts:382`.
- 수락된 재계약에서 REQUEST_TIME으로 계약 만료일 뒤까지 미루면, 선수가 FA로 전환된 뒤에도
  기존 수락 상태의 이벤트가 다시 READY가 된다.
- 실제 서비스 재현: `PLAYER_ACCEPTED`, `requiresUserAction=true`; 최종 확정은
  `409 재계약 대상 선수의 소속이 변경되었습니다.`
- 철회로 복구할 수 있지만 성립할 수 없는 재계약이 정상 수락 상태로 표시되고 진행을 막는다.
- 대응 방향: 응답 재활성화 전에 최신 소속/제안 유효성을 확인하고 무효 제안을 정리한다.

### 8. 공용 선수/카드/세트효과 생성 API에 인증·관리 권한 없음 — 외부 접속 허용 전 우선 수정

- 위치: `backend/src/players/players.controller.ts:19`, `backend/src/players/themes.controller.ts:19`,
  `backend/src/players/player-cards.controller.ts:21`, `backend/src/set-bonuses/set-bonuses.controller.ts:20`.
- 해당 컨트롤러와 전역 설정에 인증/관리자 guard가 없다.
- 실제 컨트롤러와 ValidationPipe를 사용하고 저장 service만 mock 처리한 HTTP 재현 결과:
  `/players`, `/themes`, `/player-cards`, `/set-bonuses` 모두 Authorization 없이 201, 생성 service 진입.
- 서버에 접속 가능한 비로그인 클라이언트가 공용 카탈로그를 추가할 수 있다. 세트효과는
  기존 세이브의 경기 계산에도 동적으로 반영되므로 관리자 전용 쓰기와 공개 조회를 구분해야 한다.
- 실제 개발 DB에 익명 데이터를 생성한 검사는 아니다.
