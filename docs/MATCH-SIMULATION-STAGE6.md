# 경기 시뮬레이션 STAGE 6 — 실제 경기 연결

2026-09-28. `lol_match_simulation_rework_v2_reviewed.md`의 STAGE 6 구현 기록이다. 사용자가 새 엔진을 실제 경기의 기본 계산기로 연결하도록 지정했다.

## 변경된 실행 경로

`MatchesService.simulate → TacticalRunsService → buildCareerEngineInput → startSimulation/runUntil → projectMatch → adaptTacticalResult → 기존 경기·선수 상태 저장`을 사용한다. 일반 경기와 Direct/Quick/Fast의 공통 경기 서비스에서 같은 코어를 호출한다. 이전 승패 추첨과 합성 스탯 생성기를 새 경기 결과에 호출하지 않는다.

- 실제 넥서스 파괴로 `FINISHED`가 된 경기만 승자·스탯·경기 후 컨디션을 확정한다.
- `HORIZON_REACHED` 또는 코어 오류는 결과/커리어 보상을 만들지 않는다. 입력과 상태를 진단 가능하게 보존한다. 기존 코어의 일부 조합이 60분에 끝나지 않는 한계는 남아 있다.
- 기존 완료 경기 결과와 과거 관전 경로는 보존한다. 새 엔진의 과거 경기 재계산은 하지 않는다.
- 시리즈는 기존 밴픽·선택권·누적 피어리스 저장 경로를 사용한다. 자동 진행에서는 같은 밴픽 AI에 결정을 위임한다. 감독이 직접 진행하는 밴픽/세트 경계는 유지한다.
- 단독 경기 역시 실제 10개 챔피언을 합법적으로 자동 드래프트한다. 지원하지 않는 진행 중 구형 가상 픽 카탈로그는 명시적으로 거절한다.

## 저장·재접속

추가 테이블은 `match_tactical_runs`, `match_tactical_chunks`다. 실행권/입력/체크포인트와 결과 경기의 연결을 분리하여 경기 계산 동안 긴 DB 트랜잭션을 유지하지 않는다.

- career/series/game 기반 실행 키, DB 고유 제약, 커리어 잠금과 실행 lease로 중복 실행·최종 반영을 보호한다.
- 엔진/룰셋/카탈로그/입력과 seed, RNG·사건 원장을 포함한 체크포인트를 고정한다. 재요청은 저장된 입력으로 이어진다.
- gzip 체크포인트는 경기 시간 60초 이상 진행되고 직전 저장 후 실제 시간 5초가 지났을 때 저장한다(아래 2026-10-04 최적화). 코어는 경기 시간 1초 구간마다 이벤트 루프를 양보한다. 프로세스당 한 개 실행으로 메모리 사용을 제한한다.
- 최종 경기·스탯·선수 컨디션 변경과 run의 match 연결은 같은 트랜잭션에서 확정한다. 이미 연결된 실행은 선수 상태를 다시 갱신하지 않는다.
- 계산 중이거나 결과 반영을 기다리는 경기가 있으면 같은 커리어의 선수/날짜/피드백 변경을 차단한다. 같은 세트의 재개·최종 반영만 해당 실행 키로 허용한다. 재개 준비 중에는 날짜 이벤트나 리그 준비에 따른 변경을 반복하지 않는다.
- Fast 재시도는 이미 시작한 경기를 먼저 재개한다. AI 경기는 처리 한도에 포함하고, 감독 팀은 고정된 한 세트만 마친 뒤 다음 의사결정 지점에서 멈춘다. 다른 경기나 잘못된 세트 번호로 실행권을 재사용할 수 없다.
- 리플레이 조회는 기존 계정/커리어 소유권을 확인한다. 클라이언트가 입력·체크포인트·경기 중 명령을 제출하는 API는 추가하지 않는다.

API는 `GET /matches/:id/tactical-run`, `GET /matches/:id/tactical-run/chunks/:index`다. 완료 경기 DTO의 `tacticalReplay`가 새 관전 화면 연결을 지정한다. 과거 경기는 이 필드가 없다.

## UI·리포트

`replay.ts`는 실제 프레임과 같은 사건/보상 원장을 순회해 시점별 KDA·획득 골드·지갑·CS·피해·아이템을 만든다. 원래 사건 sequence를 유지하며 내부 공격/자연 골드 사건을 모두 브라우저에 보내지 않는다. 각 청크는 최대 256 KiB다.

`TacticalMatchViewer`는 필요한 구간만 조회하고 최대 세 청크를 캐시한다. 재생 커서는 커리어/경기/엔진/입력 해시별로 분리된다. 탭이 숨겨지면 재생이 멈추고 배속·탐색은 서버 계산을 호출하지 않는다. 지도·체력·지표·중계는 동일한 마지막 저장 프레임 시점까지만 표시한다.

현재 스냅샷은 2초 간격이다. 두 프레임 사이의 실제 경로 변경/CC를 알 수 없으므로 임의 직선 보간 대신 마지막 확정 위치를 유지한다. 따라서 부드러운 연속 이동은 아직 구현하지 않았다. 관전은 전지적 시점이며 AI 관측과 별개다.

최종 승자/리포트는 재생 종료 시점에 표시한다. 실제 골드의 소수점은 저장하고 GD@15/CSD@15는 15분 전에 종료하면 `null`/`—`로 보존한다. 경기 평점과 경기 후 컨디션 갱신에는 기존 표시/커리어 함수를 사용하되 그 값으로 승패나 원장 수치를 다시 생성하지 않는다.

이전 최종 승률 공식의 전략·메타·세트 보너스 가산값은 새 코어에 중복 적용하지 않는다. 현재 새 코어의 중립 메타, 근사 스킬/아이템, 미지원 기능 범위는 [STAGE 3–5](MATCH-SIMULATION-STAGE3-5.md)와 [환경 모델](TACTICAL-ENVIRONMENT-MODEL.md)을 따른다. 활성 세트 보너스와 원래 선수 상태는 스냅샷에 보존하지만 이전 합성 엔진의 세트 보너스 효과 전부를 실제 행동 모델로 옮긴 것은 아니다.

## 실행 환경 적용

기존 배포 환경의 `backend/.env`와 DB 연결을 준비한 뒤 `npm.cmd run migration:run`, `npm.cmd run schema:verify`를 실행하고 서버를 다시 시작해야 한다. `synchronize`와 자동 마이그레이션은 계속 꺼져 있다.

최초 STAGE 6 작업 환경에는 `.env`, DB 연결 환경변수, MySQL/Docker 실행 도구가 없어 실제 DB 마이그레이션과 DB E2E를 실행하지 못했다. 이후 로컬 MySQL 환경에서 확인한 수정·적용 결과는 아래와 같다.

## 로컬 MySQL 실연동 보완

실제 작업 공간에는 STAGE 6 코드가 커밋되어 있었지만 개발 DB에는 36개 마이그레이션만 적용되어 있었고 리플레이 테이블이 없었다. 다음 문제를 수정하고 실제 DB 적용까지 확인했다.

### 기존 기록과 소수점 보존

- MySQL의 TypeORM `changeColumn`은 타입 변경 시 `DROP COLUMN / ADD COLUMN`을 생성한다. `1789768800000`의 골드·15분 지표 변환을 `ALTER TABLE ... MODIFY COLUMN`으로 바꾸어 기존 값을 보존했다. 반대 방향 변환도 같은 방식을 사용하며 소수점·미관측 값이 있으면 롤백을 거부한다.
- 네이티브 MySQL JSON에 실제 리플레이를 저장했다가 읽으면 일부 부동소수점 값이 바뀌었다. 1분 입력으로 재현했고, 첫 청크의 직렬화 크기가 174,656 → 174,472 bytes로 변하면서 해시도 달라졌다. 이로 인해 실제 관전 청크 API가 409를 반환했다.
- `1789855200000`은 실행 입력·드래프트·manifest·청크를 **JSON 텍스트를 그대로 담는 longtext**로 변환한다. 공유 transformer로 직렬화/복원하고 기존 해시·크기 검사는 유지한다. gzip 체크포인트는 기존 binary 저장을 유지한다. 이미 손상된 외부 환경의 구형 리플레이를 해시만 바꾸어 정상인 것처럼 처리하지 않는다.
- 실행 기록이 남은 상태에서 네이티브 JSON으로 되돌리는 롤백은 거절한다.

### 관전 복구

경기 저장 직후 POST 응답이나 후속 시리즈 GET 응답이 끊겼을 때, 원래 세트 번호를 유지해 멱등 재요청한 뒤 **같은 경기의 실제 리플레이를 먼저 표시**한다. 결과창을 먼저 열어 승패를 노출하거나 다음 세트를 새로 계산하지 않는다. 이전 엔진 경기의 관전 경로도 유지한다.

### 이번 검증 결과

- 백엔드 123 suites / **1,549 tests 통과**, 타입 검사·빌드·변경 TypeScript ESLint 통과.
- 프론트 `test:*` **33개 스크립트 모두 통과**, 타입 검사·빌드 통과. 실제 브라우저 수동 검사는 하지 않았다. Vite의 500 kB 청크 크기 경고는 남는다.
- 새 격리 MySQL E2E **3개 검사 통과**: 실제 소수점/청크 해시 왕복, 기존 정수 지표 업그레이드·호환 롤백 보존, 실제 경기 API부터 저장·관전 조회·권한·중복 요청 검사.
- 실제 경기 표본: seed 123, 양 팀 기본 능력 85, 케미/균형 숙련도 70, 정식 자동 밴픽. **경기 시간 약 46분에 실제 넥서스 파괴**, 리플레이 92청크, 선수 10명의 저장 지표와 엔진 보고 일치. 완주 결과를 주입하거나 테스트용 승자를 만들지 않았다.
- 실제 API 계산·검증 시간은 Jest/MySQL 환경에서 **약 217초**였다. 첫 시도는 300초 테스트 제한으로 중단되어 완료 검증에 실패했다. 이후 Jest의 Math 전역 조회 비용을 줄이고 테스트 제한을 600초로 두었다. 두 번째 시도에서 JSON 저장 문제를 발견했으며, 최종 수정 후 위 3개 검사를 모두 통과했다. 이 시간은 배포 환경의 성능 보장이 아니다.
- 완료 경기 재요청은 같은 match ID를 반환하고 경기 수·폼·컨디션을 중복 갱신하지 않았다. 다른 계정의 경기·청크 접근은 404, 인증 없는 접근은 401, 계산 중 중복 실행은 409로 거부했다.
- 개발 DB의 마이그레이션 **38개 적용**, `schema:verify` 일치 확인. 백업 후 기존 데이터 7개 테이블의 전체 행 해시를 전후 비교해 `changedTables: []` 확인: 세이브 21개, 커리어 팀 404개, 커리어 선수 2,036명, 선수/카드 각 310개, 경기 291개, 선수 경기 지표 2,910개 보존.
- 사전 SQL 백업은 Git 제외 경로 `backend/.tmp/stage6-backup/`에 보관한다. 테스트용 DB들은 종료 시 제거·제거 확인했고 기존 커리어에서 테스트 경기를 생성하지 않았다.

재현 명령은 `backend`에서 `npm.cmd run test:e2e:isolated -- --testPathPatterns=tactical-runs.e2e-spec`이다. 이 테스트는 임시 DB 이름 검사를 통과해야 실행되며 개발 DB 직접 실행을 거절한다.

현재 로컬 환경은 스키마 적용까지 끝났으므로 **최신 백엔드를 재시작하면 새 경기부터 실제 엔진·리플레이 경로를 사용**한다. seed 재실행이나 과거 경기 재계산은 필요 없다. 모든 조합의 종료율, BO5 전체 실경기 완주, 장시간 계산 최적화까지 완료됐다는 뜻은 아니다.

## 2026-10-04 계산 비용 및 운영 AI 보완

### 결과를 바꾸지 않는 최적화

- CPU 표본에서 지형 가시성/벽 충돌 검사가 주요 비용이었다. 완전히 동결된 맵의 벽 모서리 연결 그래프만 WeakMap으로 재사용한다. 움직이는 유닛이나 판단 결과를 캐시하지 않으며, 경로의 순서·동점 처리·부동소수점 계산을 유지한다. 가변 맵은 캐시하지 않는다.
- 체크포인트는 동기 직렬화 중 변경될 수 없는 상태를 다시 `structuredClone`하지 않는다. v1 JSON 형식과 전체 canonical SHA-256 검증은 그대로 유지한다. gzip 레벨 1로 압축 비용을 낮춘다.
- 체크포인트 주기를 경기 시간만으로 정하지 않고 실제 계산 시간 5초와 경기 시간 최소 60초를 함께 사용한다. 마지막 저장 이후 약 5초의 계산 + 한 구간 계산/직렬화/DB 쓰기 정도가 장애 시 재계산 대상이다. lease heartbeat는 독립적으로 유지하며, 경기 판단에 실제 시각을 사용하지 않는다.

### 새 경기의 운영 AI

이 단계에서는 `rules.macroAi = COORDINATED_V1`을 새 경기 입력에 고정했다. 현재 신규 경기 기본값은 아래 재점검에서 추가한 `COORDINATED_V2`다. 이 필드가 없는 저장 경기와 이미 시작한 시리즈는 기존 판단을 계속 사용한다. 다음 세트는 직전 경기들의 고정 정책을 조회해 일치하는 정책으로 만들며, 섞인 정책은 거부한다. 엔진의 승패/피해 판정 자체를 바꾸거나 세이브를 초기화하지 않는다.

- 오브젝트 선택을 선수별 최단거리 경쟁에서 팀 단위 목표·참가 인원 배정으로 보완했다. 실제 이동 시간·HP·DPS·관측 적·정글러 합류를 평가하고 불필요하게 전원을 부르지 않는다. 시작/포기/Smite는 기존 물리 도착·사거리·시야 검사를 거친다.
- TOP이라는 이유만으로 항상 사이드를 맡기지 않는다. 이니시에이터는 본대에 합류하고, 사이드에 적합한 TOP/MID 챔피언이 건강한 팀 인원·오브젝트 계획·공성 버프를 보고 분할 압박을 맡는다.
- 근처에서 함께 공격할 수 있는 적과 캐리를 위협하는 적을 집중 공격 대상으로 평가한다. 숨은 적의 현재 좌표/HP를 읽지 않는다.
- 실제 장기전에서 **기지 방어 대상인데도 더 가까운 외곽 타워 웨이브를 선택하는 오류**를 발견했다. 긴급 방어 인원은 실제 위협받는 기지 구조물을 우선하도록 고쳤다. 해당 상황의 회귀 테스트를 추가했다.

### 완주 및 저장 검증

- 백엔드 전체 **125 suites / 1,566 tests 통과**. 타입 검사·Nest 빌드와 변경 실행 경로/테스트의 ESLint 검사도 통과했다. 프론트 코드는 이번 작업에서 변경하지 않았다.
- 새 정책의 초기 개발판에서는 seed 125 첫 세트가 60분 시간 초과였다. 이를 승리로 처리하지 않았으며, 기지 방어 대상 선택 수정 후 같은 입력이 실제 넥서스 파괴로 끝났다.
- 최종 새 정책으로 **실제 자동 밴픽 BO5 한 시리즈가 1:3, 네 세트 모두 넥서스 파괴로 종료**했다. 경기 시간은 각각 38분 00.9초 / 40분 55.4초 / 46분 33초 / 43분 53.6초였다. 15분 JSON 체크포인트에서 재개한 네 세트의 전체 상태 해시가 직접 실행과 일치했고, 피어리스 사용 픽은 40개였다. 실제 3승 시 종료하며 5세트를 강제로 만들지 않았다. 임시 선수 입력을 사용한 DB 없는 시리즈 검사다.
- 최종 MySQL 격리 E2E 3건 통과: 새 정책이 실제 입력에 저장되는지, 넥서스 종료·선수 10명 지표·103개 리플레이 청크 저장/조회, 소유권·중복 요청 방지를 확인했다. 실제 경기 시간 약 51.30분, Jest/MySQL API 계산·검증 약 151.1초였다. 다른 검증과 병행했으므로 앞선 217초나 위 DB 없는 벤치마크와 직접적인 성능 비교로 사용하지 않는다.
- 임시 E2E DB는 생성한 대상만 제거하고 제거를 확인했다. 이번 작업은 개발 DB의 선수·커리어·경기 데이터를 수정하지 않으며 추가 마이그레이션/seed도 필요 없다.
