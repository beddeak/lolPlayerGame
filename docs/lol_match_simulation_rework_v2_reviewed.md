## 0. 적용 범위·근거·공통 계약

### 0.1 현재 구현을 먼저 확인

스크린샷만 보고 기존 코드가 ‘랜덤 이동 + 근접 전투’라고 확정하지 않는다. 이는 조사할 가설이다. 이동·시야·판정이 정상이어도 좌표 변환, 보간, 시간 불일치, 오래된 스냅샷으로 화면이 이상할 수 있다.

현재 저장소의 실제 파일·호출 경로·테스트로 원인을 확인한다. 기능이 이미 있다면 재사용하고, 문서에만 있으면 미구현으로 구분한다.

기존 로그인, 계정/세이브 소유권, Player/PlayerCard/CareerPlayer, 계약, 이적시장, 피드백, 커리어 캘린더를 임의로 교체하지 않는다. 현재 패키지 버전과 DB 마이그레이션 방식을 따른다.

### 0.2 사실과 설계를 구분

- `[R#]`: 부록 D에 있는 외부 공식 자료.
- `검증된 기준`: 해당 자료의 특정 패치/범위에 관한 정보.
- `게임용 모델`: 본 프로젝트가 채택할 추상화·알고리즘·검증 기준.
- `미확정`: 실제 자료 또는 사용자 결정이 필요한 값. 임의 확정하지 않는다.

공식 자료가 서로 모순되거나 패치 적용 범위가 불명확하면 문제를 기록한다. 선택한 Ruleset을 실행하는 데 필요한 미확정 값은 승인된 게임용 값으로 명시하거나 해당 규칙의 활성화를 막는다. 조용히 0, 100, 임의의 시간으로 채우지 않는다.

### 0.3 2026 전체를 하나의 패치로 취급하지 않는다

각 Ruleset은 `id`, `version`, `gameMode`, `sourcePatch`, `sourceReferences`, `modelRevision`, `capabilities`, 검증 상태를 가진다.

다음은 **26.1 시점의 변경사항을 확인할 때 사용할 근거**이지, 2026 모든 대회·후속 패치의 최종 수치표가 아니다.

| 항목 | 확인한 기준 | 근거 |
|---|---|---|
| 첫 미니언 생성 | 00:30 | [R1] Game Start Time |
| 주요 첫 정글 캠프 | 늑대·블루·레드·칼날부리 00:55, 돌거북·두꺼비 01:07 | [R1] Game Start Time |
| 첫 바위게 | 02:55 | [R1] Game Start Time |
| 바론 최초 생성 | 20:00 | [R1] Game Start Time |
| 공허 유충 | 25.09에서 08:00, 재생성 제거로 변경 | [R2] Void Epic Monsters |
| 협곡의 전령 | 25.09에서 15:00 출현으로 변경 | [R2] Void Epic Monsters |
| 위 유충·전령 시간의 연결 | 26.1은 별도 명시한 것을 제외한 에픽 몬스터 출현 시간을 유지한다고 설명 | [R1] Game Start Time |
| 포탑방패 | 외곽 방패가 14분에 사라지는 옛 규칙을 그대로 적용하지 않음 | [R1] Outer Turrets |
| 역할 퀘스트 | 역할별 진행·보상 추가/변경 | [R1] Role Quests |
| 2025 요소 | 아타칸·핏빛 장미·무력행사 제거 | [R1] Atakhan, Blood Roses, Feats, and Kills |

후속 패치를 선택하면 관련 변경 이력을 따로 확인한다. 위 표만으로 최신 패치 검증 완료를 주장하지 않는다. Swiftplay/신속 모드, ARAM, Classic의 시간을 일반 소환사의 협곡에 혼합하지 않는다.

원문의 `10:04 전령 획득` 예시는 위 출현 규칙과 맞지 않아 폐기한다. 대체 로그도 실제 Ruleset과 실행 결과에서 생성한다. `20분 바론`이라는 원문의 설명 자체는 확인한 26.1 기준과 맞으므로 오류로 분류하지 않는다.

### 0.4 현실 규칙과 추상화 수준

일반 경기의 넥서스 승리 조건, 구조물, 골드·경험치·상점의 큰 흐름은 공식 입문 자료 [R5]를 참고한다. 세부 수치·예외는 선택한 Ruleset으로 고정한다.

역할 퀘스트, 포탑 특수 규칙, 시야 확장 요소, 귀환·이동 보정처럼 운영에 영향을 주는 기능은 각각 `정확 모델 / 근사 모델 / 미지원` 여부를 기록한다. 근사 모델을 실제 2026 전체 규칙과 동일하다고 표시하지 않는다. PBE 프리뷰 [R6]와 출시 패치가 충돌하면 출시 자료를 우선한다.

챔피언 유형 기반 모델을 유지한다. 단, HP·사거리·성장·자원·공격/보호 행동이 없는 상태에서 실제 전투를 구현했다고 하지 않는다.

### 0.5 데이터와 ID

- `careerId`: 독립된 세이브 세계.
- `seriesId`: BO1/BO3/BO5 시리즈.
- `gameId`: 시리즈 안의 한 세트.
- `careerPlayerId`: 해당 세계의 연도별 선수 개체.
- `actorId`: 해당 세트의 참가 개체.
- `variantId`: 픽의 실제 식별자. 선수 이름·이미지로 대체하지 않는다.

2013 버전과 2026 버전의 동일 선수가 동시 출전할 수 있으므로 닉네임 또는 Player 원본 ID로 런타임 상태를 합치지 않는다. 경기당 실제 선발 5명씩만 actor로 참여한다.

### 0.6 시간 3종 분리

`careerDate`는 커리어 날짜, `simTimeMs`는 해당 세트의 정수 경기 시간, `playbackTimeMs`는 클라이언트 재생 위치다.

화면 배속, 브라우저 FPS, 사용자 PC 속도, 네트워크 지연이 경기 결과를 바꾸지 않는다. 경기 30분 진행이 커리어 30일 진행이 되어서는 안 된다.

### 0.7 입력과 스냅샷

시리즈 환경에는 Ruleset, MetaProfile, 맵, 픽 카탈로그, 엔진·평가 모델 버전을 고정한다. 각 세트에는 선발, 현재 능력치/상태, 전술, 역할, 픽, 주문, seed를 별도 스냅샷으로 저장한다.

진행 중인 세트에 DB 최신 선수 능력치나 최신 메타를 자동 주입하지 않는다. 세트 사이 변경 가능한 항목은 별도로 처리한다.

세트 시작 시 두 팀/진영, 실제 10명, 선발 포지션, Variant 소유/사용 제약, 역할·주문을 검증한다. 이미 도입한 비주류 픽을 이름만 보고 금지하지 않으며, 지원되지 않는 픽은 의미 있는 오류를 반환한다. 누락된 숙련도를 자동 100으로 채우지 않는다.

### 0.8 절대 유지할 불변식

모든 행동은 존재하는 대상, 실제 위치, 유효한 경로, 소요 시간, 자원, 생존·행동 상태를 검증한다.

한 개체가 동시에 두 장소에 있거나, 이미 소비된 보상을 다시 받거나, 원거리에서 상대를 근접 공격하거나, 죽은 뒤 새 행동을 선택하는 상태를 허용하지 않는다.

현재 코드에 없는 기능은 자동으로 구현된 것으로 간주하지 않는다. 실제 테스트를 실행하지 않았다면 통과라고 보고하지 않는다.

### 0.9 단위·범위·모델 경계

시간은 정수 경기 밀리초, 이동은 명시한 월드 거리 단위를 사용한다. CSS 픽셀과 월드 거리를 섞지 않는다. 비율 0~1, 표시 백분율 0~100, 선수 능력치 0~100을 필드별로 구분한다.

Mechanics 95는 챔피언 공격력 95가 아니다. 선수 능력은 판단·실행 모델에, 챔피언/장비 수치는 피해·방어 모델에 사용한다. 서로의 단위를 직접 더하지 않는다.

정수/고정소수점 또는 명시적 반올림 정책을 선택하고 적용 경계가 배속에 따라 달라지지 않게 한다. HP·자원은 정의된 범위, 비용은 비음수, 확률은 유효 범위에서 검증한다. NaN·Infinity·음수 경과시간은 즉시 진단한다.

상수·가중치·정규화 범위는 버전이 있는 설정으로 관리한다. 누적 보정의 상한과 적용 순서를 정의하고, 모든 항목을 무조건 곱해 능력이 0 또는 무한대로 가는 공식을 피한다.

## 1. 가장 중요한 설계 원칙 — 관측 → 판단 → 행동 → 결과

각 팀은 자신이 알고 있는 상태로 목표를 선택한다. 각 선수는 팀 계획, 개인 지시, 현재 위험을 종합해 의도를 가진다.

```text
팀별 관측 상태
→ 실행 가능한 후보 계획
→ 예상 이득·시간·비용·위험 평가
→ 팀 계획과 선수 임무 배정
→ 실제 이동·행동
→ 상대의 독립적 대응
→ 발생한 결과
→ 관측 갱신·다음 판단
```

움직임은 의사결정의 결과다. 그러나 모든 움직임이 중앙 감독의 명령이어야 하는 것도 아니다. 급박한 회피, 딜교, CS 확보, 안전 거리 유지는 선수의 국소 판단으로 수행한다.

명백히 불가능한 행동은 RNG로 살리지 않는다. 가능한 선택 중 판단 차이·실행 오차를 확률적으로 표현한다.

## 2. Simulation과 UI 분리

순수 계산 코어는 NestJS Controller, MySQL Repository, 브라우저 애니메이션에 종속되지 않게 한다.

```text
Application Service: 권한·입력·저장·실행 작업 관리
Simulation Core: 입력 스냅샷 + 상태 + 난수 상태 → 다음 상태와 사건
Projection/Report: 허용된 화면 정보·경기 지표 생성
Frontend: 상태 재생·보간·상호작용
```

DB에서 매 틱 선수를 다시 읽지 않는다. 필요한 데이터를 시작 시 로드한다. 저장 체크포인트와 결과 확정은 애플리케이션 계층이 담당한다.

한 세트 사전 계산 후 재생하는 방식과 서버에서 구간별 계산하는 방식 중 기존 구조에 적합한 것을 택한다. 두 방식 모두 같은 코어를 사용한다. 필수 사용자 선택이 필요한 세트 경계를 넘어 다음 세트를 미리 확정하지 않는다.

## 3. Map Zone만으로 이동·전투를 판정하지 않는다

Zone은 전략적 구역이고 좌표는 판정에도 필요하다. `같은 Zone = 공격 가능`은 금지한다.

맵 데이터는 최소 다음을 가진다.

- Zone ID, 중심·경계, 의미 태그.
- 실제 통행 가능한 노드/경로, 길이·교차점·위험 지점.
- 각 레인의 웨이브 경로와 구조물 위치.
- 캠프, 오브젝트 둥지, 기지, 시야 지점.
- 벽·차단 구간과 합법적인 특수 이동 연결.

선수 위치는 경로상의 진행 거리 또는 검증된 2D 위치로 관리한다. 이동은 속도와 경과 시간에 따라 진행하며, 렌더러도 같은 경로를 따른다. Zone을 바꾸는 순간 목적지에 도착시키지 않는다.

전투에는 거리·유효 경로·필요한 시야·사거리 조건이 따로 있다. 이동기·점멸·텔레포트는 허용 대상과 자원/쿨다운/시간을 소비하는 별도 행동이다.

맵의 상단·하단, 아군·적군, 블루·레드를 구분한다. 관전 시점 회전은 렌더 좌표만 변환한다. 진영 색을 바꿨다고 탑/바텀 또는 오브젝트 위치 의미가 뒤섞이면 안 된다.

## 4. 초반 Lane Phase — 시간 강제가 아닌 기본 임무

기본 배치는 TOP 탑, MID 미드, ADC·SUPPORT 바텀, JUNGLE 캠프·갱 동선이다.

하지만 ‘14분까지 무조건 해당 라인에 있어야 한다’는 규칙은 두지 않는다. 귀환, 인베이드, 로밍, 갱 대응, 오브젝트 지원, 명시적으로 지원되는 스왑은 합법적 예외다.

각 이탈에는 목적, 출발 조건, 예상 비용, 복귀/대체 담당 계획이 있어야 한다. `전술이 TOP_CARRY`라는 이유 하나만으로 서포터가 바텀에 돌아가지 않는 상태를 만들지 않는다.

시작 이동·첫 캠프·첫 웨이브는 Ruleset에서 읽는다. ‘1분 30초부터 정글 시작’ 같은 옛 시각을 서비스에 하드코딩하지 않는다.

## 5. Lane State — 실제 웨이브의 요약

`wavePosition`, `pushAdvantage`, `pressure`는 실제 웨이브 상태에서 파생한다. 서로 무관한 랜덤 숫자로 만들지 않는다.

최소 모델:

```text
Wave/Cohort: id, lane, ownerTeam, spawnAt, pathProgress,
             살아 있는 유닛 수/종류, 체력 또는 체력 풀, 보상 내역
LaneState: 현재 웨이브들, 충돌 위치, 타워 상태, 압박 추정, 안전성
```

모든 미니언을 정교하게 조작할 필요는 없다. 묶음 모델을 쓰더라도 각 처치·유닛 수·보상은 일관되게 추적한다.

아무 챔피언이 없어도 양쪽 미니언과 포탑은 상호작용한다. 비운 라인의 미니언이 무한정 쌓이거나 CS 자원이 영원히 대기하지 않는다.

빠르게 밀기, 천천히 쌓기, 홀드/프리즈를 지원할 때는 상태와 비용을 정의한다. 상대 진영으로 조금 밀었다는 이유만으로 항상 안전한 로밍 창이 생기지 않는다. 웨이브 충돌·타워 진입, 상대 정리 속도, 다음 웨이브, 도착 시간까지 고려한다.

## 6. CS·Gold·XP — 단일 원장

한 미니언 또는 캠프 구성원의 죽음은 한 번만 해결한다. 막타, 보조 보상, 글로벌 보상, 퀘스트 보상은 Ruleset이 정한 별개의 지급 항목으로 기록한다.

CS는 처치 이벤트의 규정된 크레딧으로 집계한다. 정글 캠프 CS 표시 단위를 라이너 CS와 무조건 같다고 가정하지 않는다. 서포터 아이템 공유 예외는 별도 규칙으로 처리한다.

XP는 거리·참여·역할·공유 규칙을 따른다. 골드 공유와 XP 공유는 같은 공식이 아니다. 파밍 범위 밖에서 라인 골드를 받지 않는다. 합법적인 자연 골드·팀 보상은 별도로 계속 지급할 수 있다.

다음을 분리한다.

```text
earnedGold: 경기 중 획득액
walletGold: 지금 쓸 수 있는 금액
spentGold: 구매에 소비한 금액
inventory/buildState: 실제 확보한 장비 효과
xp / level: 경험치와 레벨
```

지갑에 든 미사용 골드를 구매한 아이템처럼 전투력에 반영하지 않는다. 시작 자산·환불·특수 보상이 있다면 원장에 구분한다. 각 지급원은 고유 사건 ID로 중복 방지한다.

LanePressure와 Laning은 웨이브 처리·딜교·막타 기회에 영향을 주되, 기회와 자원이 없는데 CS를 생성하지 않는다.

## 7. Jungle Pathing — 캠프 상태가 있는 계획

캠프에는 위치, 생존 상태, 남은 몬스터, HP, 생성/재생성 조건, 보상, 리셋 규칙이 있다.

정글 계획 후보는 FULL_CLEAR, THREE_CAMP_GANK_TOP/BOT, INVADE_TOP/BOT, COUNTER_GANK, COVER_LANE, OBJECTIVE_SETUP 등이다. 실제 코드에는 유효한 식별자명을 사용한다.

순서를 선택할 때 이동 시간, 정리 시간, HP·전투 자원, 정글 퀘스트, 라인 지원, 상대 마지막 관측, 남아 있을 것으로 예상되는 캠프를 평가한다.

보이지 않는 적 캠프가 살아 있는지 확정적으로 읽지 않는다. 이동 후 비어 있음을 발견하면 계획을 수정한다.

PathingCreativity는 가치 있는 비정형 경로를 탐색하는 능력이지, 캠프 없이 레벨을 얻거나 벽을 통과하는 능력이 아니다.

## 8. Gank — 행동의 결과를 나중에 분류

갱 후보에는 아군 접근 시간, 상대 웨이브 위치, 체력, 아군 CC/기동성, 시야 추정, 적 지원 도착 가능성, 포탑 위험, 버리는 캠프·웨이브를 포함한다.

갱을 선택하면 실제로 이동한다. 도착 전에 상대가 귀환하거나 안전하게 빠지면 계획을 포기할 수 있다.

`SUCCESS_KILL`, `FORCED_RECALL`, `SUMMONER_ADVANTAGE`, `FAILED`, `COUNTER_GANKED`는 실행 후 사건을 요약한 분류다. 먼저 성공/킬을 뽑아 놓고 애니메이션과 HP를 거기에 맞추지 않는다.

킬 없는 압박, 점멸 사용 강요, 웨이브 커버도 유효하다. ‘이득 없음’과 ‘실패해서 손실 발생’을 구분한다.

## 9. Recall — 채널링·회복·구매·복귀

일반 흐름:

```text
귀환 결정 → 안전 위치 이동 → 채널 시작
→ 중단 또는 완료 → 기지 도착 → 회복·구매 → 복귀 경로
```

채널 시간, 중단 조건, 강화 귀환 등 예외는 Ruleset과 현재 버프에서 읽는다. 귀환 중 계속 공격하거나 파밍하지 않는다. 완료 전에 기지로 순간 이동하지 않는다.

귀환 즉시 무조건 HP·마나를 전부 채우기보다 선택한 회복 모델로 처리한다. 단순화했다면 명시한다. 구매는 상점 접근 조건을 만족할 때만 수행한다.

동시 귀환은 가능한 운영이지 필수 스크립트가 아니다. ADC만 귀환하고 서포터가 시야를 잡는 식의 합리적인 분업을 허용한다.

`Condition`은 선수의 커리어 컨디션이다. 챔피언이 귀환했다고 선수의 피로까지 초기화하지 않는다.

## 10. Objective — 존재·시간·비용이 있는 목표

용, 유충, 전령, 바론, 장로 등을 Ruleset의 개별 정의로 관리한다. 공허 유충은 전령과 동일 개체로 대체하지 않는다.

최소 상태:

```text
id/type, pitId, spawn 조건, lifecycle, HP, level/scaling,
현재 공격 대상, reset/leash 상태, 획득/처치 시각, 다음 생성 조건
```

현재 존재하지 않는 전령으로 교환하는 계획을 만들지 않는다. 같은 둥지를 사용하는 개체들은 출현·소멸 순서가 충돌하지 않아야 한다.

TAKE, CONTEST, TRADE, GIVE, SETUP은 팀의 의도다. 획득은 실제 피해·처치 결과로 결정한다.

포기해도 반드시 반대편 이득을 얻는 것은 아니다. 교환할 자원이 없으면 손해를 감수하고 방어·정리·회복해야 한다.

## 11. Objective Setup — 순서가 아니라 작업 의존성

‘90초 전부터 무조건 5명 집합’ 대신 준비 예상 시간을 계산한다.

준비 계획에는 웨이브 정리, 귀환·구매, 이동, 시야 확보, 보호/커버, 사이드 담당을 포함할 수 있다. 모두 매번 실행할 필요는 없다.

```text
MID: 웨이브 처리 → 합류
SUP: 필요한 구매 완료 → 안전 경로 시야
JGL: 근처 캠프 또는 SUP 커버
ADC: 성장과 합류 시점 조절
TOP: 사이드 유지 / 합류 / 사용 가능한 TP 검토
```

각 작업의 담당자, 선행 작업, 예상 완료·실제 완료, 실패 조건을 둔다. 서로 양보하느라 영원히 기다리지 않도록 중단·대체 행동을 정의한다.

오브젝트를 준비하는 동안 반대편 라인이 계속 진행된다.

## 12. Vision — 공급원에서 계산

Zone별 NONE/LOW/NORMAL/HIGH/CONTROLLED는 UI 요약으로 사용할 수 있다. 그 값만으로 영구적인 안전·공격 버프를 주지 않는다.

시야 공급원은 챔피언, 미니언, 포탑, 와드, 명시적으로 지원하는 특수 효과다. 위치·범위·시작/종료·파괴/무력화 상태를 가진다.

와드는 사용 가능 수량, 설치 사거리/시간, 지속 시간, 탐지·제거 행동을 검증한다. 방문하지 않은 곳의 시야를 능력치만으로 즉시 채우지 않는다.

시야 준비에는 시간과 위험이 든다. 지원 없이 위험 구역에 들어가면 회피·철수·피격이 가능하다. 특수 시야 지점은 Ruleset capability로 지원 여부를 기록한다.

## 13. Fog of War — 진실 상태와 팀별 지식 분리

`WorldState`는 실제 상태이고 `TeamObservationState`는 각 팀이 이용 가능한 정보다. AI 평가 함수에 WorldState를 그대로 넘기지 않는다.

관측 정보에는 마지막 위치·시각, 관측 출처, 신뢰도, 가능한 이동 범위, 마지막으로 확인한 주요 자원을 둔다.

적의 실제 현재 위치, 보이지 않는 HP·골드·캠프, 미관측 스킬 쿨다운을 직접 읽지 않는다. 공개 규칙으로 확정되는 정보, 실제로 본 정보, 추정치를 구분한다.

관측이 끊기면 가능한 위치 범위가 시간·속도·경로에 따라 넓어진다. Macro가 높아도 추정이 자동으로 정답이 되지 않는다.

관전 화면의 전지적 시야와 팀 AI의 시야는 별개다. 디버그 화면이 상대 계획을 보여준다고 AI 입력에도 들어가면 안 된다.

## 14. Fight Trigger — 국소 교전은 병렬로 발생

갱·역갱·다이브·시야 교전·카정·픽오프·사이드 맞대결·바론 전환·기지 방어 등 상황 근거를 기록한다.

가까워지는 것은 기회일 뿐 강제 전투가 아니다. 반대로 상대가 공격하면 적극적 교전 의도가 없던 선수도 맞거나 방어해야 한다.

여러 곳에서 교전이 동시에 일어날 수 있다. 바텀 갱 중 탑 딜교·미드 파밍이 중단되지 않는다. Encounter가 겹치면 같은 피해가 두 번 처리되지 않도록 참가자/사건을 통합하거나 공통 Resolver에서 해결한다.

멀리 있는 선수는 도착 예정일 뿐 현재 전투원으로 계산하지 않는다.

## 15. Engage Decision — 이길 확률만 보지 않는다

교전 판단은 해당 팀의 관측으로 예상하는 국소 전력, HP·중요 자원, 성장, 접근 경로, 아군 도착 시간, 적 추정 지원, 시야, 목표 가치, 실패 비용을 평가한다.

평가 값의 단위를 정규화한다. 골드 3,000과 능력치 90을 무가공으로 더하는 식을 피한다.

불리하면 후퇴할 수 있지만 ‘4대5면 무조건 후퇴’, ‘골드가 밀리면 용 금지’ 같은 절대 규칙은 두지 않는다. 상대의 큰 자원 소모, 고립, 기지 붕괴나 결정적 목표를 막아야 하는 상황도 고려한다.

진입 후 상황이 바뀌면 추격 중단·재배치·철수가 가능해야 한다.

## 16. Numbers Advantage — 도착 시간까지 계산

현재 공격/지원 가능한 인원과 일정 시간 후 도착할 수 있는 인원을 분리한다.

가까워 보여도 벽·경로·CC·체력 때문에 지원이 늦을 수 있다. TOP의 TP는 실제 보유·사용 가능·대상·시전/도착 시간을 검증한다.

아군 합류 예상과 적 합류 추정은 확실도가 다를 수 있다. 동일한 정보를 모든 팀에게 보장하지 않는다.

인원 우위를 활용했는지는 실제 합류·교전·목표 진행 이벤트로 평가한다.

## 17. Teamfight — 고정 장면 순서가 아닌 전투 루프

원문의 ENGAGE → BURST → PEEL → CARRY DAMAGE 순서는 설명용으로만 사용한다. 보호는 폭딜보다 먼저도, 지속딜과 동시에도 일어날 수 있다.

각 전투 업데이트/사건에서 다음을 처리한다.

- 사거리와 경로에 맞는 위치 조정.
- 살아 있고 행동 가능한 공격/보호 대상 선택.
- 공격 또는 스킬의 준비·자원 소비·발사·적중·효과.
- 보호막·피해 감소·회복·CC·시전 중단·쿨다운.
- 죽음·철수·추격·새 합류자 반영.

모든 챔피언의 스킬 전체를 복제할 필요는 없다. Variant의 소수 행동 슬롯과 실제 효과·비용으로 추상화한다. 아무 행동 정의 없이 ‘Engage 90이므로 킬’로 처리하지 않는다.

공격 피해는 이미 발생한 성장·장비·역할 수행·메타 효과를 사용한다. 팀 OVR을 마지막에 다시 곱하거나 추가 승패 추첨으로 결과를 뒤집지 않는다.

## 18. Fight Result — 사건 집계

1:0 교환, 서로 철수, 킬 없는 점멸 소모, 3:2 교환, 전멸은 실제 HP·죽음·주문 사건에서 집계한다.

결과표를 먼저 고른 뒤 사망자를 분배하지 않는다.

전투 직후 남은 HP, 소모 자원, 상대 부활·합류 시간, 웨이브, 실제 오브젝트 상태를 확인한다. 한 명을 잡았다고 자동으로 용, 두 명을 잡았다고 자동으로 바론을 지급하지 않는다.

추격보다 귀환이 좋은 경우, 목표보다 넥서스 공략이 좋은 경우도 비교한다.

## 19. Death·Respawn — 한 번만 처리

사망 전이 시 그 생명 주기의 DeathEvent를 한 번만 발행한다. 처치 기여, 골드/XP, 현상금, 버프 처리, 부활 일정을 동일한 사건에서 연결한다.

죽은 actor는 새 이동·공격·귀환·목표 판단을 하지 않는다. 이미 발사된 투사체나 지속 효과의 생존 여부는 효과 정의를 따른다.

부활 후 기지에서 다시 출발한다. 이동 시간 없이 원래 위치로 복귀하지 않는다.

부활 시간은 Ruleset의 레벨·시간·예외 규칙을 사용한다. 모든 포지션의 최대 레벨을 하나의 상수로 단정하지 않는다.

## 20. Tower·Inhibitor·Nexus — 게임 종료까지 연결

구조물은 HP, 상태, 대상 가능 여부, 공격/보호 규칙, 보상 청구 상태를 가진다.

각 레인의 외곽→내곽→억제기 포탑→억제기, 기지 구조물과 넥서스의 공격 가능 조건을 선택한 Ruleset에 맞게 구현한다. 방어 구조물이 남아 있는데 마음대로 넥서스 HP를 깎지 않는다.

포탑 어그로, 미니언의 역할, 백도어 보호, 방패 지급은 필요한 최소 모델부터 연결한다. 이미 지급한 방패·파괴 보상을 다시 받을 수 없다. 재생성 구조물의 보상 재지급 여부도 명시한다.

억제기 파괴/복구와 웨이브 압박은 실제로 연결한다. 미구현이라면 capability에 표시한다.

**정상 경기 종료는 유효한 넥서스 파괴 사건으로 결정한다.** 운영이 잘됐다는 이유만으로 승리를 바로 지급하지 않는다. 별도 기권 모드를 지원할 때만 검증된 기권 규칙을 사용한다. [R5]

## 21. Lane Assignment — 14분 자동 이동 제거

라인 재배치는 타워 상태, 퀘스트 진행, 웨이브, 다음 목표, 생존 위험, TP, 픽과 역할 숙련도를 보고 결정한다.

ADC가 미드로 이동하고 TOP/MID가 사이드를 나누는 것은 가능한 배치 중 하나다. 서포터는 ADC와 항상 붙어 있어야 하는 actor가 아니다.

기존 라인 담당자가 떠나고 새로운 담당자가 도착하기까지의 공백과 비용을 처리한다. 두 캐리가 같은 웨이브 골드를 모두 받지 않는다.

초반 의도적 라인 스왑과 중반 라인 재배치는 다른 기능이다. 초반 스왑은 별도 지원·검증이 끝나기 전 기본 비활성으로 둔다.

## 22. Side Lane — 압박과 안전의 균형

사이드 담당은 웨이브 처리, 타워 위협, 탈출 가능성, 적 관측, 팀의 반대편 상황을 함께 본다.

깊이 미는 만큼 보상 기회와 고립 위험이 커질 수 있다. 상대가 수비하러 왔는지는 관측 또는 불확실한 추정으로 처리한다.

상대 인원을 묶었다면 반대편 팀원이 그 시간 안에 실제로 움직여야 이득이 된다. 사이드가 밀렸다는 플래그만으로 팀 골드를 추가하지 않는다.

SPLIT_PUSH, SIDE_LANE_MID, Macro는 판단과 실행에 사용하고 타워 데미지·이동속도·골드 보상을 무제한 중복 증가시키지 않는다.

## 23. Cross-map Trade — 양 팀 독립 계획의 결과

A팀이 용을 시도하는 동시에 B팀은 유충, 전령, 타워, 캠프, 웨이브, 귀환 중 현재 가능한 대안을 평가한다.

모든 교환 후보는 실제 존재·도달·처리 가능 여부를 확인한다. 같은 둥지의 출현 전 개체를 거래 대상으로 삼지 않는다.

교환이 성립했는지는 양 팀의 실제 사건으로 집계한다. 반드시 공정한 금액으로 보상을 맞출 필요는 없다. 한쪽이 대응을 늦게 해서 아무것도 얻지 못할 수도 있다.

이 기능 때문에 월드 전체에 단 하나의 전술 상태를 강제하지 않는다.

## 24. Baron Gameplay — 점수 버튼이 아닌 위험한 작업

SETUP, START, BAIT, TURN, BURST, DISENGAGE는 계획·행동 단계다.

현재 바론 HP, 우리 팀 피해/생존 가능성, 중요 자원, 상대 접근 추정, 웨이브와 시야를 사용한다. 시작할 때부터 끝날 때까지 실제 시간이 흐르고 참여자가 피해를 받을 수 있다.

바론 공격 중인 선수는 동시에 다른 목표에 동일한 공격량을 무료로 넣지 않는다. 일부만 공격하고 일부는 차단하는 분업은 가능하다.

정글러가 살아 있다는 이유로 확보 확률 100%를 주지 않는다. 강타/확보 행동은 범위·자원·HP·사용 시각이 있는 액션이다. 스틸과 리셋도 실제 상태에서 발생한다.

획득 버프의 대상, 지속, 사망 시 처리, 미니언 강화·귀환 효과 등은 Ruleset과 capability에 명시한다. 버프 획득이 자동으로 타워·승리를 생성하지 않는다.

## 25. Match State — 전역 생명주기와 전장 상황 분리

전역 상태는 CREATED, RUNNING, PAUSED, COMPLETED, ERROR 같은 생명주기로 한정한다. 상태명은 기존 구조에 맞춰 조정한다.

LANING, OBJECTIVE_SETUP, CROSS_MAP, SIDE_LANE_PRESSURE, BARON_DANCE, SIEGE, BASE_DEFENSE는 단 하나의 배타적 전역 상태가 아니다.

각 팀/라인/Encounter에 동시에 존재할 수 있는 상황 또는 UI 요약 태그로 관리한다.

용 준비 중 탑 파밍, 바론 대치 중 바텀 수비가 동시에 진행되어야 한다.

## 26. Team Plan — 지속·변경·실패 조건

계획은 ID, 목표, 담당 임무, 시작 시각, 완료 조건, 무효화 조건, 재평가 시점, 유지 보너스/전환 비용을 가진다.

유효하면 잠시 유지하되, 목표 소멸·담당자 사망·합류 불가·새로운 위협이 생기면 재평가한다.

매 틱 점수가 근소하게 바뀌었다고 왕복하지 않도록 hysteresis를 사용한다. 반대로 120초가 되기 전엔 무조건 같은 계획을 강제하지 않는다.

길찾기 실패, 반복 귀환 취소, 끝없는 추격, 상대가 오기만 기다리는 대치에는 안전한 대체 행동과 진단 로그가 있다.

## 27. Shotcaller — 오더 품질과 실행 품질 분리

Macro·ObjectiveSense는 계획의 판단 품질, Shotcalling은 전달·우선순위 정리, TeamPlay와 팀 숙련도는 맞춰 실행하는 품질로 연결한다.

오더 담당을 서포터로 고정하지 않는다. 기존 선수 데이터와 감독 설정을 활용한다. 서포터 전용 항목만 있는 현재 스키마라면 호환 어댑터와 확장안을 제시한다.

높은 오더 능력도 보이지 않는 적 위치를 알거나 합류 시간을 삭제하지 못한다.

낮은 팀합은 반응·합류 오차를 만들 수 있지만 의도적인 순간이동·무한 우왕좌왕·계속 자살로 표현하지 않는다.

## 29. Team Strategy — 선택을 유도하되 강제 스크립트 금지

TOP_CARRY, TOP_JUNGLE, MID_CARRY, MID_JUNGLE, UPPER_SIDE, BOT_CARRY, BOT_PRESSURE, BALANCED를 현재 모델에 맞춰 연결한다.

전략은 개입·성장 배분·합류·픽 선호를 바꾼다. 실제 자원은 유한하다.

TOP_CARRY라도 바텀에 무시하면 큰 손해가 나는 위험이 있거나 상체 행동이 불가능하면 적응한다. Weak Side에게 무조건 죽으라고 지시하지 않는다.

전략의 설명과 실제 자원·행동 비율이 맞는지 집계한다. 전략 UI만 바뀌고 결과가 동일한 구현은 완료가 아니다.

## 30. Proficiency — 계층별 한 번씩 적용

포지션, 역할, 유형/Variant, 팀 전략, 팀합을 분리한다.

낮은 숙련도는 선택·실행 타이밍, 보호 연계, 자원 낭비, 적절한 거리 확보에 제한적으로 영향을 준다. 같은 약점을 피해량·적중·생존·최종 승률에 반복 적용해 선수를 무력화하지 않는다.

각 스탯/숙련도에 대해 `원본 값 → 계산 함수 → 적용 대상 → clamp → 기록 지표`를 제출한다.

현재 게임에서 등장한 익숙하지 않은 역할은 실제 경험을 쌓을 수 있지만 세트 도중 무제한 영구 성장하지 않는다. 기존 커리어 성장 처리 경계를 유지한다.

## 31. Meta — 중립 어댑터부터, 주류 흐름만

메타 기능이 아직 없으면 지원된 것처럼 가정하지 않는다. 우선 중립 `MetaEnvironment`를 연결해 기존 엔진이 실제 소비할 인터페이스를 마련한다.

향후 쌍포, 초중반 교전, 하이퍼캐리, 바텀 주도권, 성장 정글, 포킹·공성, 정면 한타, 사이드 운영을 연결한다. 특정 챔피언 조합의 반짝 전략은 이번 범위에서 제외한다.

Ruleset은 기본 규칙, Meta는 환경 효율, TeamStrategy는 감독 선택, Composition은 실제 픽 조합이다.

메타는 실제 행동·장비/유형 효율·성장 비용의 승인된 지점에 적용한다. `메타 일치 +10 OVR`이나 최종 승패 재추첨을 사용하지 않는다.

실제 골드 보상을 변경한 것과 AI가 그 목표를 더 가치 있게 평가한 것을 구분한다.

쌍포라고 무조건 강하지 않고 실제 자원·보호·유형 숙련이 필요하다. 하이퍼캐리는 경기 시간만으로 성장 완료하지 않는다.

대회/시리즈의 환경 버전을 고정한다. 공개 전 미래 메타를 AI나 브라우저에 전달하지 않는다. 전체 메타 카탈로그 구현은 이번 엔진의 선행 조건을 충족한 뒤 별도 단계로 진행한다.

## 32. Champion Archetype / Variant — 실제 행위가 가능한 데이터

Archetype은 분류, Variant는 실제 픽 개체, 선수 숙련도는 그 픽을 얼마나 잘 운용하는가다.

Variant는 최소한 자신이 사용하는 모델에 필요한 범위에서 다음을 정의한다.

```text
id, archetypeTags, allowedPositions,
성장/자원 요구, HP·전투 자원, 이동·사거리·내구,
웨이브·챔피언·구조물·몬스터 대상 공격 특성,
소수의 공격/CC/보호/이동 행동 슬롯과 비용·쿨다운
```

Early/Mid/Late는 경기 시간 기반 보정과 실제 성장 기반 효과의 관계를 명시한다. 가난한 선수가 시간이 되었다는 이유로 완성 장비를 가진 성능이 되지 않는다.

Tank라는 이유로 항상 특정 공격 방식을 강제하지 않는다. 선택한 Variant의 능력·역할을 따른다.

현재 아이콘·표시명·Variant가 서로 다르면 정합성 오류로 보고한다. 단지 탑에서 서포터 이미지가 보였다는 이유만으로 로직 오류라고 단정하지 말고, 실제 off-role 허용과 연결 데이터를 확인한다.

## 33. Fearless Draft — 작은 픽 풀 문제를 먼저 검증

이전 세트에 사용한 픽이 이후 양 팀에 제한되는 피어리스 개념은 [R4]를 참고한다. 적용 범위는 Competition Rules로 고정한다.

일반 밴은 해당 세트, 피어리스는 해당 시리즈의 누적 사용 제한이다. `variantId` 단위와 Archetype 전체 제한을 혼동하지 않는다.

두 팀 5명, 중복 픽 없이 5세트 전체 피어리스라면 그 시리즈의 선택 픽만 총 50개가 필요하다. 일반 밴과 포지션 적합성 때문에 충분한 전체 개수만으로도 드래프트 가능성이 보장되지는 않는다.

포지션마다 유형 2~3개를 만든다는 것과 Variant가 2~3개뿐이라는 것은 다르다. 픽 풀이 모자라면 캐릭터를 몰래 재사용하지 않는다. 카탈로그 확장 또는 사용자 승인된 간소화 규칙을 제안한다.

각 선택 단계에서 남은 합법적인 픽으로 양 팀의 미완성 포지션을 채울 수 있는지 검증한다. 초기 카탈로그 설정과 밴 개수도 검증한다.

2026 First Selection은 진영과 선/후픽 선택이 분리되는 규칙이다 [R3]. `mapSide`와 `pickOrder`를 별도 저장하고 자동 동일시하지 않는다. 어느 팀이 선택권을 받는지는 대회 규정으로 설정한다.

## 34. 경기 속도·킬 빈도 — 대본 목표 금지

킬 없이도 웨이브·골드·시야·구조물·목표 상태가 진행될 수 있어야 한다.

그러나 ‘프로경기니까 10분까지 킬 금지’, ‘20분 총 킬은 항상 N 이하’처럼 결과를 고정하지 않는다. 공격적인 조합과 실패가 겹치면 많은 킬도 가능하다.

현실 분포와 비교하려면 사용할 대회·기간·패치·데이터 출처를 별도 확보한다. 측정하지 않은 평균을 현실 기준이라고 만들지 않는다.

진행 정체는 실제 웨이브, 공성, 성장, 목표와 팀 계획에서 해결한다. 엔진 안전 한계에 도달하면 `SIMULATION_STALLED` 또는 오류로 중단·보존하고 진단한다. OVR이 높은 팀을 강제로 우승 처리하지 않는다.

## 35. Timeline·통계 — 같은 사건에서 생성

핵심 사건에는 gameId, 단조 증가 sequence, simTimeMs, type, actor/target, 위치, 원인 ID, 결과를 기록한다.

사용자 타임라인은 이 기록을 요약한다. 개발용 세부 이동 로그와 사용자 중계는 분리한다. 이벤트 문장을 먼저 만든 뒤 스탯을 맞추지 않는다.

통계도 동일 기록에서 집계한다.

- K/D/A: 유효한 사망·기여 규칙에서 집계. 누가 킬을 했는지 근거가 없는 사망은 별도 집계.
- DPM: 이 모델이 정의한 ‘적 챔피언 대상 피해’ / 경기 분. 포탑·몬스터 피해와 섞지 않는다.
- 피해량: pre-mitigation, post-mitigation, shield absorbed, 실제 HP 손실을 필요에 따라 분리. 공개 DPM에 어느 값을 쓰는지 고정한다. 실제 Riot 통계와 동일하다고 주장하려면 정의를 별도로 검증한다.
- KP: 유효한 (K+A) / 팀 킬. 0킬 시 0 또는 N/A 중 API 정책을 고정하고 NaN을 금지한다.
- GD@15·CSD@15: 실제 15:00 상태를 채집한다. 그 전에 종료되면 null로 두고 최종값으로 대체하지 않는다.
- Gold Share·Damage Share: 동일한 시간·분모·선발 범위를 사용한다. 0분모 처리를 명시한다.
- KDA 무데스 표시는 JSON Infinity를 보내지 말고 `perfect` 또는 유한한 표시 규칙을 사용한다.

워스트/MVP는 지시된 역할과 받은 자원·상대 압박을 고려한다. 평가는 관측된 기여 설명이지 검증 없는 단일 패배 원인 확정이 아니다.

## 36. Frontend Tactical Camera — 판정과 같은 시간축

프론트는 서버 상태/이벤트의 시각을 기준으로 위치를 재생한다. FPS나 setInterval 호출 수로 HP·킬·캠프를 계산하지 않는다.

이동은 전달된 경로를 보간한다. 두 Zone 중심 사이 직선 보간으로 벽을 뚫거나 맵을 가로지르지 않는다.

귀환 완료·TP 도착·사망·부활은 각각의 전이로 보여준다. 죽은 아이콘이 계속 이동하거나 사망 직후 딜하는 것처럼 보이지 않게 한다.

HP, 레벨, CS, 위치, 킬로그는 같은 재생 시각을 사용한다. 미래 킬로그를 현재 화면에 먼저 표시하지 않는다.

아이콘 겹침을 줄이기 위한 화면 offset은 실제 위치를 바꾸지 않고 필요 시 실제 위치와 연결선을 보여준다.

배속·일시정지·탭 비활성·재접속은 표시만 바꾼다. 이전 장면을 보는 리플레이 조작이 결과를 재계산하거나 중복 저장하지 않는다.

## 37. 팀 의도 UI — 관전과 감독 지식 분리

디버그 모드에는 실제 TeamPlan, 임무, 예상 이득·비용, 관측 근거를 표시한다.

일반 감독 화면에는 자기 팀의 계획과 허용된 상대 관측/분석만 제공한다. 상대의 비공개 미래 계획을 기본 노출하지 않는다.

전지적 관전은 명시적 표시 모드다. 그 데이터가 AI 관측 입력으로 역류하지 않게 한다.

## 38. Player Intent 디버그

Intent ID, 상태, 목표, 현재 위치, 경로, 도착 예상, 이유, 중단 조건, 관련 teamPlanId를 확인 가능하게 한다.

예시 의도는 HOLD_LANE, LAST_HIT, PUSH_WAVE, RECALL, ROAM, CLEAR_CAMP, GANK, COVER, PLACE_VISION, CONTEST_OBJECTIVE, SPLIT_PUSH, ENGAGE, PEEL, RETREAT다.

지시(ROAM_TOP), 경로 목표, 현재 행동(이동/대기/시전)을 구분한다. 현재 로밍 중이라고 모든 시간에 전투 행동이 금지되는 모델을 만들지 않는다. 허용되는 공격·이동 조합은 액션 규칙으로 정의한다.

‘왜 아무것도 안 하는지’도 기록한다. 기다림은 캠프 생성 대기·웨이브 홀드처럼 합리적인 이유와 재평가 시간이 있어야 한다.

## 39. Explainability — 판단 당시의 근거 보존

판단 시각의 관측 스냅샷/해시, 후보 행동 점수, 선택 근거, 예상 비용, 실제 결과를 연결한다.

당시 몰랐던 적 상태를 경기 종료 후 가져와 ‘알고 피했다’고 설명하지 않는다.

‘바론 시도 이유’와 ‘바론 성공 이유’는 다르다. 성공했다고 판단도 항상 좋았다고, 실패했다고 판단도 항상 나빴다고 자동 평가하지 않는다.

설명 가능한 원인이 없는 결과 문장을 생성하지 않는다. 자연어 보고서는 확인된 사건과 계산 항목을 템플릿으로 표현한다.

## 40. Randomness — 재현과 인간적 차이

엔진 내부의 Math.random, Date.now, 외부 응답 순서 등 비결정적 입력을 제거하거나 명시적 입력으로 격리한다.

seed만이 아니라 RNG 알고리즘·상태, 엔진/Ruleset/메타/카탈로그 버전, 입력 명령 순서가 재현 조건이다.

월드 일정 RNG, 경기 판단/전투 RNG, 렌더 장식 RNG를 분리한다. 이벤트 로그를 더 기록하거나 애니메이션을 바꿨다고 경기 난수 순서가 달라지지 않게 한다.

Consistency의 변동은 일정한 경기/국면 단위로 상관성 있게 유지한다. 매 프레임 전체 선수 능력을 독립 추첨하지 않는다.

행동 점수가 높은 후보도 의도·위험 성향에 따라 달라질 수 있으나 실행 불가능한 후보는 미리 제외한다.

## 41. Tick·사건 순서·동시성

팀 계획, 개인 행동 판단, 전투/시전 완료, 화면 업데이트를 같은 느린 틱으로 처리하지 않는다.

정수 경기 시간의 이벤트 스케줄러 또는 고정 스텝을 사용한다. 기존 엔진에 적합한 하나를 선택하고 문서화한다.

거시 판단 주기는 느릴 수 있지만 사망·도착·귀환 완료·스킬 적중·쿨다운/생성 경계는 실제 예정 시각을 건너뛰지 않는다. 배치 진행은 모든 필요한 사건을 순서대로 처리해야 한다.

같은 결정 시각에는 양 팀이 동일 시점의 자신들 관측으로 의도를 만든 뒤 해결한다. A팀 전체 갱신 결과를 B팀만 먼저 보는 편향을 만들지 않는다.

동시 효과·치명타·상호 사망 등 같은 시각 충돌 처리 규칙을 명시한다. 어떤 상황에서 이미 발사된 공격이 사망 이후 도착할 수 있는지도 효과 정의를 따른다.

동일 타임스탬프의 중립적 충돌 해결을 팀 배열 순서/DB ID 우선으로 만들지 않는다. 필요한 타이브레이크는 고정된 공정 정책 또는 저장된 난수로 처리한다.

## 42. State Machine — 병렬 계층

```text
MatchLifecycle
  ├─ Team A Observation → Plan → Tasks
  ├─ Team B Observation → Plan → Tasks
  ├─ Actor별 생존/이동/행동/효과 상태
  ├─ Lane/Wave·Camp·Objective·Structure 상태
  └─ 다중 Encounter → 공통 Action Resolver
          ↓
       동일 사건 원장 → 상태/통계/리플레이
```

팀 계획이 선수에게 목표를 주더라도 귀환 중단·생존 회피 등 실제 상태가 실행 가능성을 결정한다.

하나의 거대한 enum에 모든 시스템 조합을 넣지 않는다. 계층을 무한히 늘리는 범용 프레임워크도 만들지 않는다.

## 43. 현재 코드 감사 — 확인한 것만 보고

실제 호출 경로를 읽고 다음을 제출한다.

| 조사 | 보고 방식 |
|---|---|
| 이동·좌표 변환 | 파일/함수, 상태 원천, 보간 방식 |
| 교전·피해·사망 | 트리거, 시간 해상도, 집계 경로 |
| 웨이브·캠프·경제 | 보상 생성·소비·XP 근거 |
| 시야·AI 입력 | WorldState 누출 여부 |
| 오브젝트·구조물 | 출현·획득·종료 판정 |
| 전술·숙련도·메타 | 실제 소비 함수와 장식 필드 |

사용 가능한 재현 입력·seed·시간 구간을 기록한다. 경로 왕복인지, 실제 순간이동인지, 단순 화면 스냅인지 분리한다.

기존 테스트를 실행한 결과와 실행하지 못한 이유를 구분한다.

## 44. 구현 순서 — 의존성 보완

### STAGE 0: 감사·재현·보호

기존 실행·회귀 결과, 저장소 구조, 호환성 경계, Ruleset 후보, 실제 문제를 보고한다. 기존 세이브 백업·개발 전용 테스트 환경을 확보한다. 대규모 변경은 승인 전 시작하지 않는다.

### STAGE 1: 공통 기반과 최소 액션

Game snapshot, ID, 시간, 난수, 경로 이동, 최소 관측, HP/자원, 공격·피해·죽음, 귀환·복귀, 보상 원장을 만든다.

**HP·이동 시간·피해·관측 없이 갱 성공률만 먼저 구현하지 않는다.** 최소 전투 Resolver를 만들고 후속 한타 단계에서 확장한다.

### STAGE 2: 자연스러운 초반 0~10분

웨이브·XP·CS, 캠프·동선, 딜교, 조건부 갱·역갱, 로밍·커버, 상점 구매를 연결한다. 현재 Ruleset에서 이 시간대에 활성화되는 목표도 검증 가능한 최소 처리 또는 명시적 capability 상태로 관리한다.

목표: 이동·파밍·체력·복귀·판단 이유가 일치하는 초반. 특정 킬 스코어 재현이 목표가 아니다.

### STAGE 3: 시야·오브젝트·맵 변화

시야 자원과 추론, 용/유충/전령 등, 준비·포기·교환, 타워와 라인 재배치. 포탑방패·역할 퀘스트 등 선택한 Ruleset의 운영 영향도 필요한 수준으로 연결한다.

### STAGE 4: 팀 전투와 중후반 운영

같은 Resolver에 CC·보호·재배치·도착·철수·국소 동시 교전을 확장한다. 사이드·바론·공성·기지 방어·넥서스 종료까지 연결한다.

### STAGE 5: 전술·숙련도·메타·피어리스 검증

중립 인터페이스로 먼저 연결된 전술/숙련도를 검증하고, 준비된 메타 기능만 단계적으로 활성화한다. 피어리스 픽 풀과 다섯 세트 전체 흐름을 검사한다.

### STAGE 6: UI·리포트·저장·성능 검증

UI 동기화는 각 단계에서 병행하되 마지막에 배속·재접속·세트 전환·대량 시뮬레이션 회귀를 묶어 검증한다.

단계 간 기존 기능이 있으면 재사용한다. 이 순서는 기존 코드를 전부 삭제하고 처음부터 만들라는 지시가 아니다.

## 45. 자연스러움·정합성 테스트

부록 B의 필수 테스트를 구현 단계별로 연결한다.

시나리오 테스트는 **입력 조건이 충분히 명시된 상황**에서 기대 행동을 확인한다. ‘골드가 밀리면 언제나 도망’ 같은 일반 법칙으로 만들지 않는다.

정합성·불가능 행동 테스트는 엄격하게, 밸런스·경향성 테스트는 여러 seed와 통계로 평가한다. 테스트를 맞추기 위해 시나리오 ID를 엔진에서 if문으로 처리하지 않는다.

실행 명령, 환경, seed 집합, 버전, 성공·실패 개수, 남은 실패를 보고한다.

## 46. 금지사항

- 원인을 읽지 않고 기존 엔진이 랜덤이라고 단정한 전면 교체.
- 같은 Zone이면 공격, Zone 변경이면 도착하는 방식.
- 실제 자원 없이 CS·XP·아이템·와드·쿨다운 생성.
- 정해진 시각·골드 차이·메타명만으로 강제 집합/포기/승패 결정.
- 진실 상태를 AI에 넘기고 ‘추론’이라고 부르는 구현.
- 고정 전투 결과를 골라 킬·HP·이동 로그를 역으로 작성.
- 지시마다 모든 보정을 곱해 무한히 증폭/약화.
- 가용 픽이 없는데 피어리스 몰래 해제.
- UI의 재생 배속·호출 횟수로 결과 변경.
- 승리·보상·시즌 순위 중복 저장.
- 구버전 경기 결과와 기존 세이브를 몰래 재계산.
- 실제 DB 초기화나 불필요한 의존성 대규모 업데이트.
- 테스트 미실행을 통과로 보고.

## 47. 최종 목표와 완료 기준

관전자가 목적과 비용을 이해할 수 있어야 한다.

‘용 준비를 위해 라인을 처리하고 귀환했다’, ‘전투가 불리해 시도는 포기했지만 타워 교환이 가능했다’, ‘상대가 빨리 복귀해서 바론을 끝내지 못하고 철수했다’ 같은 설명이 실제 이벤트와 맞아야 한다.

정적인 파밍 구간과 빠른 전투 구간이 같은 상태를 이어받는다. 결과, 맵, HP, 스탯, 리포트가 서로 모순되지 않는다.

공통 필수조건: 불변식 테스트 통과, 기존 기능 회귀 확인, 동일 입력 재현, 저장/복구 일관성, 종료 판정, 성능 측정, 미지원 규칙 공개.

‘완벽한 실제 롤 복제’나 ‘무오류’는 명세만으로 선언하지 않는다. 검증한 범위와 남은 한계를 구분한다.

## 48. Codex가 지금 할 첫 작업

우선 STAGE 0만 수행한다. 저장소를 읽고 아래를 보고한 뒤 승인을 기다린다.

1. 현재 엔진과 UI의 실제 처리 흐름, 관련 파일·함수.
2. 확인된 오류와 아직 의심인 문제의 구분, 가능한 재현 입력.
3. 기존에 유지·재사용할 코드와 최소 수정 범위.
4. 선택할 Ruleset의 검증된 값·근사 값·미확정 값.
5. STAGE 1~2 의존성, 실제 변경 파일, MySQL 영향.
6. 테스트 명령·실행 결과, 추가할 테스트와 예상 성능 측정.
7. 기존 세이브·로그인·피드백·커리어 데이터 보호 방법.

승인 전 전면 리팩토링·DB 파괴 작업을 하지 않는다. 승인 후에도 단계별로 구현하고 검증한다.

# 부록 A. 저장·실행·재생 계약

## A1. 실행 모델

NestJS 애플리케이션 계층에서 계정 소유권, career/series/game 상태, 선발·픽·버전을 검증한 뒤 실행 입력을 고정한다.

경기 중에는 코어가 DB를 조회하지 않는다. CPU 사용량을 실제 측정하고, 장시간 작업은 작은 청크 또는 제한된 Worker Pool을 검토한다. Node의 worker_threads는 CPU 중심 작업에 사용하는 선택지다 [R9]. 무조건 새 분산 서비스나 Redis를 추가하지 않는다.

선수 한 명마다 Worker를 띄우지 않는다. 동일 게임의 상태 해결은 결정적이어야 한다. 서버 부하를 줄이려고 빠른 모드에서 다른 간이 승패 공식을 사용하지 않는다.

## A2. 세트 단위 감독 개입

기존 기획대로 팀 전술, 선발 교체, 개인/팀 피드백은 허용된 세트 사이 구간에서 적용한다. 화면 일시정지와 경기 중 자유 지휘 권한을 혼동하지 않는다.

Quick Sim의 자동 코치는 명시적으로 위임한 의사결정만 수행한다. Direct와 결과 비교 시 같은 결정 시퀀스를 사용해야 한다. 자동 코치가 다른 결정을 했다면 다른 결과가 정상일 수 있다.

한 세트의 HP·골드·레벨·쿨다운은 다음 세트 시작 상태로 재설정한다. 커리어 컨디션·폼·신뢰 및 피어리스 누적은 각자 보존 규칙을 따른다. 일회성 피드백을 재생할 때 중복 적용하지 않는다.

## A3. 체크포인트

재개에 필요한 값은 다음을 포함한다.

```text
입력/환경 버전, simTimeMs, RNG 상태,
actors, 이동 경로·진행도, action/cooldown/effect,
team observations, plans/tasks,
waves/camps/objectives/structures,
진행 중 encounters, 예정 사건 queue,
stat accumulators, ledger/sequence cursor
```

정수·열거형·nullable 규칙과 JSON 스키마 버전을 명시한다. 난수 seed만 저장하고 진행 상태가 없는 체크포인트를 ‘재개 가능’이라고 하지 않는다.

Snapshot과 사건 sequence가 다른 시점으로 저장되지 않도록 한다. 저장된 체크포인트 이후 미커밋 계산은 폐기 후 동일 입력으로 재실행할 수 있어야 한다.

## A4. 결과 확정과 중복 요청

gameId별 단일 실행권·상태 버전 또는 동등한 원자적 조건으로 중복 시작을 막는다. 메모리 플래그만으로 다중 프로세스 실행을 보호했다고 하지 않는다.

실제 시뮬레이션 전체 동안 DB 트랜잭션을 열어두지 않는다. 입력 확정·체크포인트·최종 커밋처럼 짧은 경계에서 사용한다.

결과, 스탯, 시리즈 점수와 필요한 다음 처리 이벤트는 한 번만 확정한다. 고유키 및 조건부 상태 전이로 재요청·재시작을 처리한다. TypeORM 트랜잭션 내부에서는 전달받은 transactional manager를 사용한다 [R7].

계산 실패 시 완료 승리로 꾸미지 않는다. ERROR 상태·원인·재현 정보를 보존한다.

## A5. 구버전과 마이그레이션

마이그레이션을 사용하고 실제 DB 초기화·dropSchema·무단 seed 재실행을 금지한다. 데이터가 있는 환경에서 synchronize로 변경을 밀어넣지 않는다 [R8].

완료 경기의 결과는 보존한다. 진행 중 구버전 게임은 기존 엔진으로 재개하거나 명시적인 버전 호환/중단 정책을 제안한다. 새 엔진으로 조용히 바꾸지 않는다.

엔진 교체 후 모든 옛 seed가 같은 경기 결과여야 하는 것은 아니다. 대신 기존 저장 결과 보존과 **새 버전 안에서의** 재현성을 검증한다.

## A6. 출력·성능

모든 내부 틱을 개별 DB 행과 거대한 브라우저 JSON으로 전송하지 않는다. 리플레이는 필요한 상태·핵심 사건·간격별 스냅샷을 청크로 구성한다.

한 경기/한 시리즈/여러 경기에서 실행 시간, 최대 메모리, 이벤트 수, DB 쓰기 수, 리플레이 크기를 측정한다. 목표 수치는 환경·기존 기준 측정 후 승인한다.

디버그를 꺼도 결과는 같아야 한다. 로그에는 비밀번호·토큰·개인정보를 기록하지 않는다.

## 미확정 세부값 처리

이 문서는 용·장로의 모든 생성/재생성 숫자, 몬스터별 HP/보상 전체, 이동·방어 수식, 모든 포탑 예외를 숫자로 확정하지 않는다. 이는 의도적이다. 원문에도 없었으며 패치별로 다른 값을 검증 없이 만들어 넣지 않기 위함이다.

구현 시 실제 선택한 Ruleset의 필수값 표를 완성하고 출처 또는 승인된 근사 모델을 붙인다. 예를 들어 공식 문서의 개요와 세부 목록이 구조물별 방패 적용에서 상충하면 임의로 해석하지 말고 해당 필드 검증을 별도로 남긴다.

모든 필수값이 확정되기 전 해당 모델을 ‘완전한 2026 규칙 재현’으로 출시하지 않는다. 그와 별개로 승인된 근사 모델의 시뮬레이터는 명확한 이름과 capability로 단계적으로 실행·검증할 수 있다.
