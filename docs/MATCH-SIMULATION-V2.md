# 행동 기반 경기 코어 — 개발 현황

2026-09-28: 실제 경기 계산·저장·관전 연결은 [STAGE 6 구현 기록](MATCH-SIMULATION-STAGE6.md)을 따른다. 아래의 미연결 설명은 STAGE 1–2 당시의 기록이다.

2026-09-27 갱신: STAGE 3–5 opt-in 전체 맵 코어는 [MATCH-SIMULATION-STAGE3-5.md](MATCH-SIMULATION-STAGE3-5.md), 후속 운영 AI 보완은 [MACRO-AI-REVIEW.md](MACRO-AI-REVIEW.md)에 기록했다. 아래는 유지 중인 **STAGE 1–2 / 10분 lab 경로의 구현·검증 기록**이다. 현재 엔진 버전은 `tactical-core-3`; 이전 개발용 체크포인트는 버전 불일치로 거절하며 실제 커리어 세이브를 바꾸지는 않는다.

2026-09-26. `lol_match_simulation_rework_v2_reviewed.md`의 STAGE 0 감사 이후, 사용자가 단계별 승인 대기 없이 진행하도록 요청하여 작성한 구현이다.

## 현재 연결 상태

**기존 커리어 경기 엔진을 교체하지 않았다.** 새 코어는 `backend/src/matches/simulation-v2/`에 분리한 개발용 순수 TypeScript 라이브러리다. Nest 서비스/컨트롤러, 프론트 관전, DB 저장 경로에 아직 등록하지 않았다. 개발 DB와 완료 경기 결과를 수정하지 않는다.

STAGE 1 공통 기반과 STAGE 2의 **0~10분 실험**을 구현했다. 전체 주문서 완료나 실제 LoL의 완전한 재현을 뜻하지 않는다. 포탑·넥서스가 없으므로 이 코어는 승자나 커리어 보상을 확정할 수 없다.

| 파밍 | 정해진 시각의 개별 미니언/유한 캠프 생성. 실제 처치에서만 CS·골드·XP 발생 |

챔피언 실제 스킬, 피해 유형/관통, CC·보호, 실제 아이템 패시브, 와드, 역할 퀘스트, 구조물, 오브젝트 처치/버프, 넥서스 종료는 **미지원**이다. 유충/전령/바론은 생애주기 시각 마커만 있으며 보상을 만들지 않는다. 마나 필드는 현재 공통 자원 모델이며 챔피언별 기력/무자원을 구현한 것이 아니다.

구체적인 수치·공식 참고 출처·근사값·선수 보정 수식은 [TACTICAL-RULESET.md](TACTICAL-RULESET.md)에 기록했다. 원본 커리어 입력을 보존한 것과 모든 원본 필드를 전투에 적용한 것은 다르다.

## 코드 경계

- `input-adapter.ts`, `ruleset.ts`: 기존 게임의 읽기 전용 입력을 고정한다. 선픽/진영은 외부에서 확정하여 전달한다.
- `contracts.ts`, `world-state.ts`, `seeded-rng.ts`: JSON 계약, 입력 검증, 상태·난수·체크포인트.
- `map-paths.ts`, `observation.ts`: 실제 거리와 관측 투영.
- `actor-planner.ts`: 관측에서 의도를 제안한다. 보상이나 피해를 직접 적용하지 않는다.
- `engine.ts`: 의도의 적법성을 확인하고 이동/공격/피해/죽음/귀환을 해결한다.
- `resources.ts`, `economy-ledger.ts`: 자원 생애주기, 단 한 번의 보상 및 실제 지갑/XP/아이템 변경.
- `projection.ts`: 같은 사건/원장으로 지표·개발 프레임을 만든다. 별도 승패 공식을 호출하지 않는다.
- `backend/scripts/run-tactical-lab.ts`: DB 없이 실행하는 CLI. 합성 선수는 메모리 안에서만 만들며 seed 카탈로그에 추가하지 않는다.

`queueCommand`는 단위 시나리오를 위한 개발 인터페이스다. 사용자에게 경기 중 자유 조작 API를 연 것은 아니다. 실제 감독 전술/교체/피드백은 기존 세트 사이 정책을 유지한다.

## 실행 및 검사

저장소의 `backend` 폴더에서 실행한다.

```powershell
npm run sim:lab -- --seed 123 --minutes 10 --verify-resume
npm run test:sim:scenarios
npm test -- --runInBand --testPathPatterns=simulation-v2
npm test -- --runInBand
npm run build
```

`--verify-resume`은 5분 체크포인트를 JSON으로 왕복하여 재개하고, 중단 없는 10분 실행과 전체 상태/보고 상태/원장 해시가 일치하는지 검사한다. 10분 종료 상태는 `HORIZON_REACHED`, 승자는 `null`이다. 오류는 `ERROR`로 남으며 임의 승리를 반환하지 않는다.

초기 회귀 검사에서 발견한 문제는 테스트와 함께 수정했다.

- 적이 시야 밖으로 이동한 뒤에도 긴 사거리 때문에 공격하던 문제.
- 누락된 필수 공격력/유닛 수치가 입력을 통과하여 NaN 피해를 만들던 문제.
- 커스텀 맵의 라인 경로가 벽을 가로질러 미니언이 통과하던 문제.
- 새로 생성된 미니언에 생성 직전 시간의 이동량을 주던 문제.
- 사망/귀환 중인 상대 슬롯 때문에 다른 팀의 결정 난수 순서가 바뀌던 문제.
- 반환한 관측 객체를 변경하면 내부 마지막 관측 기록도 변경될 수 있던 문제.
- 화면용 관측 조회가 AI의 관측 기억을 갱신하던 문제. 조회를 읽기 전용으로 분리했고 실제 판단 틱에서만 기억을 갱신한다. 중간 조회 횟수를 바꿔도 실행 결과 해시가 같다.
- 여러 공격의 반올림 피해가 모두 0이면 0/0으로 NaN을 만들거나 귀환을 끊을 수 있던 문제.
- 웨이브가 전진한 뒤에도 고정 위치에서 대기하던 문제. 아군 웨이브와 공유 시야로 파밍 위치를 조정하고, 전진할 체력은 부족하지만 기존 긴급 귀환 기준보다 높던 체력 구간도 회복 계획으로 연결한다.

`test:sim:scenarios`는 실제 10분 경기 세 개(seed 1003/1027/1034)를 돌려 문제 구간 이후의 CS 증가와 미니언 처치 원장을 검사한다. 긴 시뮬레이션은 Jest VM 오버헤드를 피하도록 별도 TypeScript 명령으로 분리했고, 원인별 짧은 회귀 테스트는 기본 Jest 실행에 유지한다.

프론트 첫 빌드에서도 sandbox의 Vite 자식 프로세스 EPERM이 발생하여 같은 명령을 허용된 환경에서 재실행했다. 코드 오류와 환경 실행 제한을 구분했다. E2E를 한 번의 전체 실행에서 122개 모두 통과한 것으로 표현하지 않는다.

100 seed 재검사는 Node v24.14.0 / Windows x64, ts-node 개발 실행이다. 코어는 배포 API에 연결하지 않았다.

- 입력 준비+시뮬레이션: p50 **2.992초**, p95 **4.311초**.
- 정합성 검사·projection·JSON 직렬화 포함 경기별 시간: p50 **3.137초**, p95 **4.501초**. 100개 전체 **341.936초**.
- 배치 최대 개발 리플레이 **9.640MB**, 최대 사건 **35,892개**. seed 123의 별도 재개 검사는 리플레이 9,707,573bytes / 전체 체크포인트 11,344,704bytes.
- 전체 ts-node 프로세스 표본 최대 heap **769.1MB**, RSS **944.5MB**. GC 및 동시 개발 검증 영향을 포함하며 단일 경기의 실제 peak나 배포 성능 보장이 아니다.
- 수정 후 100개 중 96개는 0킬, 4개는 1킬. 전체 선수 합계 귀환 48~60회/경기. 정합성/관측된 정체 해소와 전투 밸런스 완성은 별개다.

위 2분 표본 검사는 모든 배회·모든 전략적 비효율을 증명하거나 배제하는 검사가 아니다. 실제 파밍 증가를 확인하는 별도 세 시나리오와 함께 해석한다.

## 현재 한계와 다음 구현 순서

1. 현재 기본공격/동일 이동속도/안전한 귀환 모델은 추격을 킬로 전환하는 빈도가 낮다. 특정 시각에 킬을 강제로 추가하지 않는다. 준비된 스킬/CC/보호 모델과 실제 협공 도착으로 전투를 확장하고, 여러 seed의 경향을 확인해야 한다.
2. 포탑이 없어 현재 라인 계획은 아군 웨이브를 따라가되 전진률 상한·적 기지 최소 거리를 사용하는 보수적인 근사다. STAGE 3에서 실제 구조물·위험·웨이브 상태와 재배치 판단을 함께 연결해야 한다.
3. 관측은 최소 시야 모델이다. 와드 재고/쿨다운, 부쉬, 탐지, 팀 추론은 아직 없다.
4. 개발 프레임은 2초 간격이다. 경로 코너·중간의 재계획을 무시하고 두 좌표를 직선 보간하면 벽을 통과해 보일 수 있다. 현재 프레임을 완성된 관전 리플레이처럼 연결하지 않는다. 실제 경로 변화 사건과 청크 전송/재생을 후속 구현해야 한다.
5. CLI 체크포인트의 해시는 손상 확인용이지 인증/권한 검증이 아니다. 실행권·소유권·DB 원자적 커밋·저장 제한은 서비스 통합 시 추가해야 한다.
6. 수 MB짜리 개발 이벤트/체크포인트를 요청 응답으로 그대로 보내거나 장시간 동기 실행을 API에 넣지 않는다. 측정 후 청크 저장/전송과 제한된 경기 단위 실행 작업을 설계한다.

다음 연결 순서는 **STAGE 3 시야 자원·오브젝트·포탑 → STAGE 4 전투/중후반·넥서스 → STAGE 5 전략·피어리스 → STAGE 6 저장/관전 통합**이다. 실제 경기 결과 경로 교체 전까지 기존 엔진과 세이브는 그대로 유지한다.
